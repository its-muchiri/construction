## What "MVP complete" means for this project
Per build-sequencing-roadmap.md, construction.co.ke is **last** in the build order — it has the highest transaction values (up to KES 5,000,000+), the longest escrow holds, and the deepest KYC requirements, so it benefits from every shared module being battle-tested on the other four platforms first. Its MVP is: equipment rental and labor-contract booking, KYC Tier 3 provider onboarding, escrow with a retention percentage, and an e-commerce store for materials/tools — built on shared modules 1–4 plus module 9 (KYC v2, Tier 3) and module 10 (Escrow & Commission Engine v2: long-hold + retention-percentage release). Equipment-condition-report workflow and milestone-based *multi-week* payment releases are technically V2 per the roadmap, but prd.md calls equipment-condition reporting this platform's single highest-leverage risk mitigation — treat it as effectively MVP-critical rather than deferring it.

- Customer can sign up / log in
- Customer can post a project request (equipment type/duration, or labor scope)
- Verified equipment owners/crews can submit quotes; customer accepts one, creating a booking
- Customer funds escrow with a retention percentage held back pending a post-completion inspection window (Tier 3 escrow behavior per shared-architecture.md's trust-tiering table)
- Provider documents equipment condition at handover and return (photo/video), feeding dispute evidence
- Provider completes Tier 3 KYC (ID, business registration, proof of ownership/insurance where applicable) before listing
- Customer can buy materials/tools/safety equipment from the store (heavy equipment stays rental-only, not store-purchasable, per prd.md)
- Customer can submit a review; damage/long-duration disputes route to an investigation path
- Every image slot (homepage hero, equipment/crew directory photos, provider portfolio photos, store product photos for materials/tools) shows a real, topically relevant photo sourced from Unsplash — not a placeholder box or broken image
- App builds and runs with zero errors, works on mobile width
- Core flow (post request → accept quote → fund escrow → condition report → complete → release funds → review) covered by a smoke test

## Known issues / open questions
- This platform's shared-module dependencies (KYC Tier 3, escrow v2 long-hold) are supposed to be proven on laundry.co.ke and rider.co.ke first per build-sequencing-roadmap.md. shared-architecture.md leaves open whether the shared modules are one library or five independent per-platform implementations ("Notes on Deployment Strategy") — if this project has its own independent escrow/KYC code rather than a shared one, verify it still matches the Tier 3 / v2 behavior spec rather than assuming parity with the other platforms.
- Equipment-damage dispute resolution speed is prd.md's stated core risk — treat any gap in condition-report evidence collection as high priority. (This pass closed the main gap here — see changelog.)
- **Found a production-breaking Postgres bug while building the escrow engine, now fixed globally: `src/Config/Database.php`'s Postgres connection had `PDO::ATTR_EMULATE_PREPARES => false`.** Neon's pooled host (the one `PGHOST` actually points at — `*-pooler.*.neon.tech`) runs PgBouncer in transaction-pooling mode, which does not tolerate native server-side prepared statements inside an explicit multi-statement PDO transaction: the second statement in any `beginTransaction()`/`commit()` block failed with `SQLSTATE[25P02] current transaction is aborted`, silently rolling back the whole transaction. This is exactly the pattern `acceptQuote` (create booking + 3 milestones) and `confirmMilestone`/`Escrow::releaseMilestone` (release + conditionally open the inspection window) need, so **every explicit-transaction write in this codebase was broken**, not just the new escrow code. Reproduced directly against the live Neon DB with a minimal repro (confirmed `EMULATE_PREPARES=true` fixes it, confirmed the same 2 statements succeed via node-postgres without the flag), then fixed it at the connection level in `Database.php` so no per-query workaround is needed. **If a future pass adds another explicit `beginTransaction()` block, this is already handled — no special handling needed per-query.**
- Also fixed a second, unrelated live bug found while smoke-testing: `ProjectController::submitConditionReport` bound a PHP `bool` for `independently_verified` — PDO stringifies `false` to `''`, which Postgres rejects for a `BOOLEAN` column (`invalid input syntax for type boolean`). Fixed by binding the literal string `'true'`/`'false'` instead. Audited the rest of the codebase for the same pattern (grepped for `(bool)` casts feeding `execute()`); no other occurrences.
- Card gateway (`PaymentController::card`) is still not implemented — no vendor is selected yet (`.env.example`'s `CARD_GATEWAY_*` are unset placeholders, and open-questions.md doesn't resolve which provider). It now fails soft (503 if unconfigured, 501 "not implemented" if someone sets the env vars without a real client behind them) rather than faking a successful charge, mirroring how `stkPush` fails soft when M-Pesa is unconfigured. prd.md calls card the more common rail for this platform's transaction values, so this is a real MVP gap, not just polish — needs a vendor decision (Pesapal/Flutterwave/DPO are the usual Kenya-market options) before it can be built for real.
- Real M-Pesa Daraja credentials (`MPESA_*`) are not configured in this environment, so `stkPush` can't be verified end-to-end against Safaricom's sandbox from here. Verified the rest of the pipeline instead by seeding a `pending` `payments` row directly (what a real `stkPush` call would have created) and POSTing a simulated Daraja callback payload to `mpesaCallback` — the same verification approach the reference implementation (laundry.co.ke) used. Escrow hold, milestone release, retention hold, inspection-window auto-release, dispute freeze/unfreeze, and provider earnings all verified this way end-to-end against the live Neon DB, then all test rows were deleted afterward.
- Real B2C payout disbursement (actually moving KES to the provider's M-Pesa/bank account) is not built — same gap as every other platform in the portfolio. `Escrow`'s payout `payments` rows are recorded with `status='pending'`, ready for a future payout-batch job.
- No admin console UI exists anywhere (KYC approval, dispute resolution, listing moderation) — Platform Admin and Site Inspector roles from prd.md's permissions table have no UI yet. `DisputeController::resolve` now has a real `account_type = 'admin'` auth guard (previously had none) and was verified this pass by temporarily flipping a test user to `admin` directly in the DB — there's no self-serve way to become an admin (correct — signup restricts `account_type` to customer/provider), but that also means an admin UI/seeded admin account is the next real blocker for using this in practice. Likely the next major checklist item.
- Store has API endpoints (StoreController) but **no page/view at all** — no `/store` route, no product listing UI, no cart/checkout UI. `store_products` table is empty (0 rows) — no seed data for materials/tools/safety equipment.
- No images anywhere in the app yet — home.php, equipment-index.php, crew-index.php, provider-profile.php have zero `<img>` tags. Needs real Unsplash sourcing per this platform's image-slot requirements once the store and listing UIs have something to show images for.
- `equipment_listings` has exactly 1 seed row, `crew_listings` has 0 — provider directory pages will render empty states against the live DB until more listings exist (either seed data or real signups).
- No automated smoke test script/harness exists yet — this pass's verification (see above) was a thorough manual curl-based run-through of the entire core flow (signup → post project → submit/accept quote → milestones auto-created → fund each milestone → release → condition reports → dispute raise/auto-evidence/resolve → final milestone retention hold → inspection window → auto-release → completed, math cross-checked: KES 300,000 total = KES 264,000 provider payouts + KES 36,000 commission), not a repeatable script. A `tests/` PHP script that replays this same sequence would be valuable for a future pass.
- **Security gap (carried over, still unresolved): `APP_KEY` is not set as a real Vercel environment variable.** Signup/login on the live deployment do work (verified again this pass), but that's because `Auth::secret()` silently falls back to a hardcoded default (`'construction-co-ke-dev-only-insecure-default-key'`) when `getenv('APP_KEY')` is empty — issuing and verifying tokens with the *same* publicly-known-in-this-repo fallback secret, not real signing. Anyone who reads this source can forge a valid bearer token for any user ID. Must run `vercel env add APP_KEY production` (or set it via the Vercel dashboard) with a real random value before this is production-safe. The Vercel CLI isn't installed in this environment, so this pass couldn't do it directly.
- Data-model gap noted, not fixed this pass: `construction_bookings`/`project_quotes` don't reference a specific `equipment_listings` row, so `submitConditionReport`'s UI just asks the provider to type in an equipment listing ID by hand rather than picking from a dropdown scoped to the booking. Low priority given the provider directory itself is still mostly unverified/unseeded.
